# Session 3 — Phase 2 design & research

**Phase:** 2 (design stage) · **Code written:** NONE

## Objective

## Research performed (measured, not assumed)
Ran targeted SQLite experiments for the mechanics P2 depends on:

1. **🔴 `DROP TABLE` cascade-deletes children when `foreign_keys=ON`.**
   Verified: a parent drop removed the child row entirely. A naive table rebuild
   would therefore silently destroy accounting data. The rebuild must set
   `foreign_keys=OFF` before `BEGIN` (the pragma is a no-op inside a
   transaction) and run `foreign_key_check` after re-enabling. Verified that a
   correct rebuild preserves the child reference.
2. **`ALTER TABLE` limits.** `ADD COLUMN` works on STRICT tables;
   `ADD COLUMN NOT NULL` without a default fails on a populated table; type,
   nullability and FK changes all require a full rebuild.
3. **Audit can be append-only at the database level** — `BEFORE UPDATE` /
   `BEFORE DELETE` triggers with `RAISE(ABORT)` rejected both. Stronger than the
   reference, where append-only is convention and ~30% of mutations write no
   audit row.
4. **No `sha256()` in SQLite** — the tamper-evident hash chain must be computed
   in Java.
5. **Partial indexes work** (`... WHERE posted = 1`) — useful for the
   posted-voucher filter every report applies.

Also re-read the reference's core accounting models to ground the schema.

## Design produced
`docs/phases/PHASE_2_DESIGN.md` — scope, schema for `company.db` core,
migration hardening (`TableRebuilder`, `schema_migration` history, baseline
fixtures), locking, backup/restore, test plan, exit criteria, risks, and four
decisions needing an answer.

Deliberate departures from the reference, each fixing a catalogued defect:
stable `system_code` on ledgers/groups (posting resolves on a code, not a

# Session 4 — API leak fix (post-review)

**Phase:** 1 (correction) · **Code written:** YES

## Trigger
The IDE flagged `AppPaths is not accessible` in `ShellApplicationIT`. Maven
compiled it fine — test code runs on the classpath, where JPMS is not enforced —
but the IDE was reading `module-info.java`, which is the real contract.

## Root cause
`CompanyService.start(AppPaths)` took a persistence type in its public
signature, forcing every caller to depend on `accubook.persistence`. The
launcher's `requires accubook.persistence` existed only to satisfy that.

## Fix
`start(Path)` + `startAtDefaultLocation()` as the public API; `start(AppPaths)`,
`companyDatabase()` and `CompanyRegistry` reduced to package-private;
`paths()` → `dataRoot()`; `requires accubook.persistence` removed from the
launcher. `accubook-app` now exposes only domain types.

Reducing `companyDatabase()` matters beyond tidiness: handing a raw `Database`
to the UI would let any layer open its own transaction and bypass the use-case
boundary — the same gap that let the reference app's Tally import bypass its
posting invariant (D-22).

## Verification
53 tests passing, 3 UI skipped. `.deb` rebuilt and the packaged app re-verified
end-to-end (`0.3000`, isolation holds).

## Observation
Second time in Phase 1 that JPMS surfaced a real layering issue the build did
not. `module-info.java` is the authority; classpath test compilation is not.

# Session 6 — Phase 3 design & research

**Phase:** 3 (design stage) · **Code written:** NONE

## Objective
Produce the Phase 3 design/research report only — research → design → report →
STOP — following the same cycle used for P1 and P2. Phase 2 accepted as complete.

## Research performed (measured, not assumed)

1. **Ed25519 is native to Corretto 17.** `Signature` and `KeyPairGenerator` both
   available; public key 44 bytes X.509 (60 chars base64, embeddable in source),
   signature 64 bytes, tampered payload correctly rejected. **No third-party
   crypto dependency is needed** — nothing extra in the jlink image.

2. **🔴 Verification costs ~1.5 ms warmed.** Far too slow to run in front of every
   mutating use case. Drove a design change: verify **once at load** into an
   immutable `Entitlement` value object, so use-case checks read a field.
   Re-verify only on token change or a periodic timer.

3. **🔴 Hardware serials need root on Linux.** `/sys/class/dmi/id/product_uuid`
   and `board_serial` throw `AccessDeniedException` as a normal user. An
   accounting application must not require root, so the fingerprint cannot depend
   on DMI. `/etc/machine-id`, MACs, CPU model and core count are readable.

4. **🔴 `NetworkInterface.isVirtual()` is unreliable.** Measured `docker0` as
   `virtual=false`. A fingerprint over "all MAC addresses" would therefore change
   when Docker, VirtualBox, a VPN or WSL is installed or removed — locking out a
   customer who did nothing. Design now uses the OS machine id primarily and at
   most the default-route MAC, as one weak signal among several.

## Design produced
`docs/phases/PHASE_3_DESIGN.md` — entitlement model (the part P4 consumes),
subscription state machine, honest threat model, composite K-of-N machine
binding, clock-tamper resistance, scope, test plan, 8 decisions, risks.

Key structural point: **the contract P4 consumes is `moduleState(moduleId)` and
nothing else.** No module imports a licence type or knows what a signature is —
which is what prevents per-module licensing logic appearing, the same drift that
left 55 of 71 reference routes unguarded.

## Problems discovered
Three of the four research findings changed the design rather than confirming it
(verification cost, DMI permissions, `isVirtual()` unreliability). Had these been
assumed rather than measured, the result would have been a fingerprint that locks
out Docker users and an entitlement check too slow for the posting path.

1. **Key ordering bug.** `Map.copyOf()` does not preserve insertion order, so

2. **Placeholder public keys were invalid.** I had written plausible-looking

4. **🔴 But `--module-path` at launch CAN smuggle a module in.** A user editing

1. **INVENTORY → SALES cycle is real.** `valuation.ts:4,162` imports and calls

# Session 9 — Phase 4 design finalisation (adversarial review)

**Phase:** 4 (design review) · **Code written:** NONE

## Inspected

## Research performed (measured, not reasoned)

1. **Reports cannot be a write bypass.** All nine report routes plus export have
   **zero** create/update/delete calls. Reads can stay ungated safely.

2. **🔴 Three non-UI write paths exist.** A scheduler creates invoices
   (`run-recurring.ts:200`); the OCR importer creates bills and invoices
   (`post-extracted.ts:270,349`); the Tally importer creates vouchers and
   **bypasses the posting core** (`tally.ts:654,688`). A UI-only guard would miss
   all three.

3. **🔴 JPMS is not a security boundary.** Built a throwaway project: a feature
   module without `requires` **cannot compile** a direct call to persistence -
   but **reflection succeeds at runtime** when the module is on the path, which
   it always is. JPMS stops accidental coupling, not deliberate bypass.

4. **Our own surface is small.** `accubook-app` is currently the only module
   requiring `accubook.persistence`.

## Decisions made
P4-1 generic viewer · P4-2 manifest diagnostic-only and **unsigned** · P4-3 keep
DORMANT and READ_ONLY separate · P4-5/P4-8 reporting splits · P4-6 invert the
accounting↔banking dependency · P4-7 split sales into invoicing and orders.

All recorded as **APPROVED ARCHITECTURAL DECISION (pending sign-off)**.

positioning, not architecture, and both are buildable.

## Contradictions discovered
1. **Finding 3 contradicts my own earlier framing.** The design described the
   persistence guard as "belt and braces". It is not - it is load-bearing,
   because JPMS is defeatable by reflection. Corrected in the design and in
   `P4_DEPENDENCY_RULES.md`.
2. The brief asks whether an absent module should be `READ_ONLY` or
   `UNAVAILABLE`. P3 already distinguishes `READ_ONLY` (installed, not
   permitted) from `DORMANT` (not installed). Recommended keeping both rather
