### 1.4 Fabricated IRN — CONFIRMED, and worse than described

`invoices/[invoiceId]/e-invoice/route.ts:122-135`:

```ts
function generateIRN(invoiceNumber, sellerGstin, fiscalYear): string {
  // In production, IRN is generated by NIC
  // This is a simulation: SHA-256 hash of invoice details
  const data = `${sellerGstin}|${invoiceNumber}|${fiscalYear}`;
  // Simple hash simulation
  let hash = 0;
  for (let i = 0; i < data.length; i++) {
    const char = data.charCodeAt(i);
    hash = ((hash << 5) - hash) + char;
    hash = hash & hash;
  }
  const hashStr = Math.abs(hash).toString(16).padStart(16, '0');
  return `${hashStr}${Date.now().toString(16)}`.substring(0, 64).toUpperCase();
}
```

The comment claims SHA-256; the implementation is a 32-bit Java-style
`hashCode` concatenated with `Date.now()`. Confirmed adjacent:
`getStateCode` returns `"27"` (Maharashtra) for **any** unmapped state
(line ~118: `if (!state) return "27"; return STATE_CODES[state] || "27";`).

## 2. Incorrect findings

### 2.1 ❌ "~300,000 lines of TypeScript" is misleading by ~3×

```
find src -name '*.ts' -o -name '*.tsx' | xargs wc -l          → 301,019
excluding src/generated (Prisma client)                        → 102,781
```

**198,238 of those lines are generated Prisma client code**, not hand-written
application source. The real hand-written codebase is **~103k lines**.

**Why this matters:** Phase 0 used the 300k figure to argue the port is a
multi-year effort. The conclusion (large effort) still stands, but the *evidence*
was inflated 3×. Any effort model built on 300k lines would be badly wrong.
Corrected figure: **~103k lines of hand-written TS**, of which ~12.7k is backend
service logic and the remainder is largely React UI and API route handlers.

### 2.2 ❌ "`applyLedgerEntries` is the single choke point" — FALSE

This was Phase 0's central architectural praise, and it is **not true**.

`src/backend/services/migration/tally.ts:697-718` deliberately **bypasses** it
with a private reimplementation, `applyLedgerBalances`, and says so:

```ts
// Apply ledger balance impact. Inlining a minimal version here
// (instead of importing applyLedgerEntries) keeps this service
// free of the posting helper's coupling — tests mock just the tx.
await applyLedgerBalances(tx, entries);
```

The inlined copy is **materially weaker** than the real one:

| Safeguard | `applyLedgerEntries` | Tally's `applyLedgerBalances` |
|---|---|---|
| Debits == credits check | ✅ throws `UnbalancedEntriesError` | ❌ **absent** |
| `organizationId` scoping | ✅ `where: { id: {in}, organizationId }` | ❌ **filters by id only** |
| Unresolved ledger handling | ✅ throws `LedgerScopeError` | ❌ **`if (!nature) continue`** |

That last row is precisely the bug the main function's comments describe having
fixed ("a voucher that balanced on paper while only some of its ledger effects
landed"). The Tally path reintroduces it.

**Consequences:** an unbalanced Tally import can post silently and put the trial
balance out permanently — and Tally import is exactly how a new customer's
historical data enters the system, so the blast radius is a customer's entire
opening position.

**This is a new defect — recorded as D-22.** It does not weaken the
recommendation to seal the posting core; it *strengthens* it considerably. The
reference app is a live demonstration that a convention-based choke point gets
bypassed by a developer with a plausible-sounding reason.

### 2.3 ❌ "MEMORY.md said the target directory is not a git repository" — needs care

The target directory is indeed **not** a git repo (verified). But an earlier
check in the previous session reported the *reference* repo's status because of
a working-directory reset. The conclusion was right; the intermediate evidence
was briefly wrong. Noted so future sessions do not trust a bare `git status`
without confirming the directory.

## 3. Partially correct findings

### 3.1 ⚠️ "Audit logging is not universal" — true, now quantified

Phase 0 said auditing was "not universal" without a number.

- `writeAudit` call sites: **89**
- Mutating route exports (POST/PATCH/PUT/DELETE): **128**

So roughly **30% of mutating endpoints write no audit row**. For a commercial
accounting product this is a compliance-relevant gap, not a stylistic one. The
desktop product should make audit emission structural (part of the use-case
execution path) rather than a call each handler remembers.

### 3.2 ⚠️ "The reference test suite is the porting oracle" — true but uneven

646 tests is real, but the distribution matters more than the total, and Phase 0
did state this. Re-confirmed: GST/TDS/payroll/posting/permissions/concurrency are
well covered; budgets, approvals, quotations, orders, cost centres, projects,
expense claims, attendance, leave, multi-currency and the entire UI have none.

Refinement: because 21 of the 646 are Playwright smoke tests **pointed at
production** (`https://accubook.tensparrows.com`), they are not a usable oracle
for a desktop port at all. The effective oracle is **625 tests**.

### 3.3 ⚠️ Bank balance is stored twice — confirmed, with detail

`BankAccount.currentBalance` is mutated directly in at least 6 places
(`receipts/route.ts:295`, `receipts/[receiptId]:102`, `payments/[paymentId]:92`,
`payroll/pay-month:209`, `bank-accounts/route.ts:113,130`) **in addition to** the
bank ledger's `currentBalance` maintained by the posting layer. Two independent
running balances for the same real-world quantity, with no reconciliation.

## 6. Architectural decisions that should be RETAINED

1. **Database-per-company (ADR-001)** — reinforced. With zero ORM/DB-level
   tenant enforcement in the reference, per-file isolation converts a discipline
   problem into an architectural property. Retained.
2. **Universal schema + modular code + signed entitlement (ADR-002)** — retained.
   It is the only model that satisfies "physically exclude modules" and "never
   delete downgraded data" simultaneously, and it avoids 2^N migration shapes.
3. **Scaled-INTEGER money + BigDecimal** — retained (see MONEY_AND_ROUNDING for
   the re-run experiments).
4. **Sealed posting core** — retained and **upgraded from 'good practice' to
   'mandatory'** on the strength of D-22.
5. **`LocalDate` for accounting dates** — retained; kills a real bug class.
6. **Enums + CHECK constraints** — retained; the reference's unconstrained
   strings caused at least two live defects (D-1, attendance vocabulary).
7. **Effective-dated statutory rule packs** — retained; the single most important
   structural improvement over the reference.
8. **Never fabricate an IRN** — retained, confirmed necessary.

## 7. Architectural decisions that should be RECONSIDERED

1. **The effort narrative** — must be rebuilt on ~103k LOC, not 300k. The
   conclusion (phase ruthlessly) is unchanged, but the justification was wrong
   and would mislead planning. **Corrected.**
2. **"Single choke point" framing** — must be restated as "*intended* single
   choke point, bypassed once in practice". The desktop design must make the
   bypass impossible rather than assume it will not happen. **Corrected.**
3. **Audit as a per-handler call** — reconsider in favour of audit emitted by the
   use-case execution pipeline, so coverage cannot drift to 70%.
4. **Denormalized running balances** (ledger and bank) — Phase 0 listed this as
   an open question (A-10). Given two independent balance stores already diverge
   in the reference, the desktop product should compute balances from the journal
   and treat any cache as a rebuildable optimisation. Strengthening the
   recommendation from "open" to "recommended: compute".

## 8. Addendum — findings from deeper validation (round 2)

These emerged from targeted re-analysis and are **not** in the Phase 0 report.
Several are more severe than anything Phase 0 recorded.

### 8.1 🔴 D-23: Credit notes and debit notes post BACKWARDS — CRITICAL

**The single most serious accounting defect in the reference application.**

`decideInvoiceEntries` (`post-invoice.ts:79-99`) has **no `CREDIT_NOTE`
branch**. Verified: `grep 'CREDIT_NOTE\|DEBIT_NOTE'` across `post-invoice.ts`
and `post-bill.ts` returns **nothing**. It unconditionally computes:

```ts
const drCustomer = taxable.plus(gst).plus(roundOff);
return { drCustomer, crSales: taxable, crGstOutput: gst, roundOff };
```

Meanwhile the UI *does* create credit notes —
`sales/credit-notes/page.tsx:242` posts `type: "CREDIT_NOTE"` — and
`invoices/[invoiceId]/route.ts:185-186` calls `postInvoiceToGl` for **any**
invoice moving DRAFT → SENT, with no type discrimination.

**Result:** issuing a credit note **debits the customer and credits sales**.
A sales return *increases* receivables and *increases* revenue. The same holds
for debit notes on the purchase side, where `bills/route.ts:22` types `type` as
a bare `z.string()` with no enum guard at all.

Impact: overstated revenue, overstated receivables, wrong GST output liability,
and a customer ledger that moves the wrong way on every return. This is
materially worse than the opening-balance bug because it affects ordinary,
routine transactions.

**Port decision: DO NOT REPRODUCE.** Credit/debit notes must be first-class,
sign-aware document types with explicit posting rules and a test asserting that
a credit note *reduces* revenue and receivables.

**This should be reported to the web application team as a live production bug.**

### 8.2 🔴 D-24: Inventory `asOf` does not filter quantities — historical reports are fiction

`valuation.ts` applies the `asOf` date **only to the cost-layer query**
(`:181`). Both `stock.findMany` (`:116`) and `loadPendingLines` (`:162`) read
**current** quantities with no date predicate.

Consequences:
- `valueClosingStock(orgId, lastYearEnd)` returns **today's quantity** priced
  with last year's layers — not a historical valuation in any sense.
- For **weighted-average items** (the default, and the silent fallback for any
  unrecognised method), opening and closing stock are computed from the *same*
  quantities, so `+ opening − closing` **cancels to zero**. The periodic
  adjustment — the entire point of the periodic model — silently does nothing.
- Reprinting last year's P&L after this year's trading gives a different answer
  every time. **Financial statements are not reproducible.**

### 8.3 🔴 D-25: Manufacturing double-counts inventory on the balance sheet

`balance-sheet/route.ts:329-331` asserts in a comment that "Stock-in-Hand is
derived from the inventory, not from a ledger". **That comment is false for any
company that manufactures.**

The `Stock-in-Hand` *ledger* (`provision.ts:78`, nature ASSETS under Current
Assets) is written by `post-wo-journal.ts:64`, so it **is** included in
`assetLedgerTotal` (`:328`). Then `:332` does
`totalAssets = assetLedgerTotal.plus(stockNow)` — adding the derived valuation
on top of a ledger balance that already reflects the same goods.

**A manufacturing company's balance sheet overstates assets by cumulative
completed production value.**

Related: the WIP journal pair is net-zero (both legs use the same `wipValue`,
and both ledgers sit in the *same* group), so it is ceremony that changes no
reported total — while still corrupting the balance sheet via the above.

### 8.4 🟠 D-26: Approval routing dead-ends for INVOICE and PURCHASE_ORDER

`route-entity.ts:36` declares `"INVOICE"` and `"PURCHASE_ORDER"` in the
entityType union, but `promote-entity.ts` has **no branch for either**
(verified: branches exist only for VOUCHER, BILL, EXPENSE_CLAIM, LEAVE).
Approvals for those types accumulate rows that never promote anything.

### 8.5 🟠 D-27: Batch quantities are never decremented
Dispatch and work-order issue adjust `Stock`, never `Batch`. Batch balances
drift permanently from actual stock. Phase 0 noted batches were "a parallel
register"; this quantifies the mechanism.

### 8.6 🟠 D-28: Leave quota is decorative
`LeaveType.annualQuota` is validated on create and **displayed** in the UI, but
`leaves/route.ts` performs **no balance check**. Employees can exceed quota
without limit.

### 8.7 🟠 D-29: Two divergent bank reconciliations, and the UI uses the untested one
The **tested** service (`banking/reconcile.ts`, with `reconcile.test.ts`)
**never writes the `BankReconciliation` model**. The **untested** 570-line
inline route (`bank-reconciliation/route.ts:481-548`) does, recomputes book
balance independently with `Number()` float math, and **is the one the UI
calls**. Phase 0 identified two implementations; it did not identify that the
tested one is the one *not* in use.

### 8.8 🟠 Stock transfers corrupt valuation two ways
- `TRANSFER` is in `INBOUND` (`valuation.ts:70`), so an internal transfer
  **fabricates a phantom FIFO cost layer**.
- Transfer-in does **not** revalue the destination's `avgCost`
  (`stock/route.ts:346-355`), so per-warehouse average costs are wrong after any
  transfer.

### 8.9 🟠 Stock adjustments post no GL entry at all
`stock/route.ts` (413 lines) contains **zero** occurrences of `voucher` or
`applyLedgerEntries`. A write-off or shrinkage reduces quantity — and therefore
silently reduces gross profit through the `− closing` term — with **no expense
ledger, no voucher, and no visible write-off line in the P&L**.

### 8.10 🟡 Returns never touch stock
Credit/debit notes are handled for GST and reporting only. No return code path
creates a `StockMovement`. Additionally the `RETURN` movement type is
unconditionally direction `IN` (`movement-rules.ts:39`), so **purchase returns
have no representable movement type at all**.

### 8.11 🟡 Scrap is costed nowhere
`fgUnitCost = wipValue / completed` (`complete/route.ts:137`) divides by
completed units **only**, so scrap's material cost is silently absorbed into
good units. No scrap account, no scrap movement.

### 8.12 Additional SCHEMA-ONLY confirmations
Beyond Phase 0's list: **Designation** (model, no route, no UI),
**multi-currency / ExchangeRate** (no conversion or revaluation anywhere — the
only app reference is a copy-through on invoice duplicate),
**ReportTemplate.schedule** (never read), **WorkOrder CANCELLED** (documented,
no endpoint).

**Missing entirely:** GSTR-4, Form 27D, FEFO batch selection, expense-claim GL
posting (there is no `voucherId` column on `ExpenseClaim`), budget-vs-actual.

**Backend-complete but no UI page:** dispatch, batches, barcode, BOMs, fiscal
years. **73 dashboard pages** exist in total.
